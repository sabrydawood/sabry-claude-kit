Rebuilt `apps/admin/app/invoices` (Est8Core admin console, `est8core-frontend/platform-master`) from a hard-coded mock to a fully backend-wired screen against `Server/Src/Modules/Admin/Admin.Billing.*` + `Billing.Service.ts`, per the golden-reference pattern already established in `app/tenants` + `app/tenant-detail`.

**Why this matters for future work on this screen (or similar billing/invoice UI):**

1. **PDF/proof/e-invoice endpoints are tenant-scoped, not admin-scoped.** `GET /invoices/:id/pdf`, `POST /invoices/:id/proof`, `POST /invoices/:id/einvoice` live under `Server/Src/Modules/Billing/Billing.Routes.ts` (tenant auth + `X-Tenant` header). There is NO equivalent route under `Admin.Billing.Routes.ts` (`/api/v1/admin/billing/*`). The admin session has no tenant token/context to call them. Do not fake these — I omitted the PDF download button from the admin invoice detail/row-actions entirely and left a note in the modal (`detailModal.pdfUnavailableNote`) rather than dead-linking or building a broken proxy. If a future request wants admin-side PDF/proof download, it needs a NEW backend route (or an admin-impersonation-token bridge) — flag it as backend work first.
2. **No aggregate money endpoint exists for invoices.** `Admin.Billing.Service#ListInvoices` only returns a paginated page + a row `count()` — never `SUM(amount)`. The mock's "Total collected" KPI cannot be honestly computed (summing only the current page would show a wrong, page-dependent number). Precedent for this exact class of gap already existed in `TenantsKpiRow.tsx` (omits the mock's "Total Users" KPI for the same reason) — mirrored that: render the KPI slot but with an honest "—" / hint copy, never fake it.
3. **No free-text search param.** `Admin.Billing.Schema#InvoiceQuerySchema` only accepts `tenantId` + `status` — no `search`. Also `Invoice.Model` has no human-readable ref number (only a UUID `id`) — the mock's `INV-2026-001` refs are fabricated demo data. Replaced the mock's free-text search box with a tenant-picker `SmartSelect` (the real, backend-supported equivalent of "filter by tenant") instead of faking client-side substring match against raw UUIDs.
4. **Tenant name resolution pattern**: invoices/refunds only carry `tenantId` (no name join anywhere in `Admin.Billing.Service`/`Billing.Service`). Built `useTenantNameResolver()` in `lib/api/hooks/useTenantNameResolver.ts`, an exact mirror of the existing `usePlanNameResolver()` pattern (fetch `useTenants({limit:100})`, build a `Map`, return a `resolve(id) => name|null` fn). This is the reusable pattern for ANY future screen that gets a bare `tenantId` back from a backend row with no join — check for a `use<X>NameResolver` before building a bespoke join/lookup.
5. **Currency-aware money formatting**: the existing `formatMoney()` in `lib/formatNumbers.ts` is hardcoded to USD (built for MRR/ARR dashboard KPIs). Invoices carry their OWN currency (SAR/EGP/AED/USD per Billing.Schema). Added `formatCurrencyAmount(amount: string|number, currency: string)` alongside it rather than overloading `formatMoney` — keep these two separate; don't retrofit `formatMoney` to take a currency param without checking every existing call site first.
6. Promoted `CURRENCY_OPTIONS` from `tenant-detail`'s route-private `_lib/editTenantOptions.ts` to shared `apps/admin/lib/currencyOptions.ts` once Invoices became a second consumer (added EGP to the list) — per AGENTS.md §2's "promote on second consumer" rule.
7. Role gating for money-moving actions mirrors the backend route guards exactly: `POST /invoices/:id/verify` and `POST /invoices/custom` are `super_admin`-only; `POST /refunds` is `admin|super_admin`. Read the current admin's role from the existing `useAuthStore` Zustand selector (`s.admin?.role`) — do NOT re-fetch `useAdminProfile()` in a page component, that duplicates the `/auth/me` call the app-wide `AuthHydrator` already made at mount.

**🔴 Nullable-fields bug (found only via LIVE data, not build/typecheck).** My original `Invoice` DTO typed `einvoiceStatus`/`taxAmount`/`taxRate` as non-null (they have `.notNull().default(...)` in the Drizzle model). WRONG: invoices inserted by the Stripe-webhook path (`Billing.Service.ts` ~1802) and by seeds omit these Billing-v2-Phase-1b columns, so the DB returns actual `null`. Three live-console bugs resulted: (1) `t('invoices.einv.' + null)` → `einv.undefined` → 32× next-intl MISSING_MESSAGE per render; (2) `formatCurrencyAmount(null, cur)` → dangling "— SAR" in the tax sub-line; (3) verbose paragraph in a KPI value slot. Fixes: made the DTO fields `| null`; added `normalizeEinvoiceStatus()` + `einvoiceLabel(status, system, t)` in `_lib/invoiceBadges.ts` (ONLY place that builds an `einv.*` key — coerces null/unknown → "none", appends `· authority` only when system truthy AND status ≠ none); added `formatTaxAmount()` (returns null on null/blank/≤0 so the caller omits the line); `computeInvoiceDetailTotals()` for null-safe modal math; KPI value → plain "—". **Lesson: a green `next build` + passing typecheck proves NOTHING about runtime i18n-key safety or null-data rendering — a DTO that claims a field is non-null is a claim about the WORST-CASE row, not the happy-path row. For any backend column added in a later migration with a DB default, assume older/seeded rows return null and type it nullable + guard every render.** Also: `browser_console_messages(all:true)` returns messages since session start — a stale authenticated session on an OLD server port polluted the dump with the very errors I'd fixed; always re-navigate and read console since-last-nav (not `all`), and confirm the port serves the NEW build (`grep new copy in .next/server`). Note: admin is behind login + enforced 2FA — an agent cannot self-complete an authenticated live render without credentials/TOTP (correctly blocked by auto-mode when scanning .env); verify via (a) grep the built `.next/server` chunks for the new code, (b) run the pure guard fns in Node against the real null shapes, (c) i18n key parity — and state the authenticated-render gap honestly.

**Gotcha hit while building:** Zod v4's `z.coerce.number()` in an RHF `zodResolver` schema breaks TS generics (`Resolver<...unknown...>` not assignable to `Resolver<...number...>`) because RHF's `useForm<T>()` expects input type === output type. Fix: use plain `z.number()` in the schema + `register(field, { valueAsNumber: true })` on the `<input type="number">` instead of `z.coerce.number()`. No existing code in this repo used `z.coerce` with RHF before this — if you see that combo elsewhere, expect the same TS error.
