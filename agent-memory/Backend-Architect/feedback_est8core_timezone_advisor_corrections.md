On the Est8Core (Server/CLAUDE.md-governed) effective-timezone task (2026-08-09), calling
`advisor()` after research but before writing code caught five things I would have shipped wrong.
Generalizable checks for this codebase (and similar ones with the same conventions):

1. **A middleware-order assumption ("X always runs before Y") is a claim, not a fact — verify it
   against EVERY routes file, not one.** I'd checked `Leads.Routes.ts` and generalized. The advisor
   made me grep `TenantMiddleware|AuthMiddleware` across all `*.Routes.ts` and cross-check against
   every caller of the function whose correctness depended on the order. **Why:** a silently-wrong
   fallback on the missed route is invisible to every gate (typecheck/tests all still pass — it's a
   RUNTIME behavior gap, not a compile error). **How to apply:** any time a fix's correctness rests
   on "middleware A always runs before B", grep the actual registration, not a sample.

2. **Every DB query in this codebase's convention is tenant-scoped by `tenantId` in the WHERE
   clause, even when a `SchemaName` (schema-per-tenant) already isolates the row.** I wrote a
   branch-timezone lookup keyed only by `(SchemaName, BranchId)`; the convention (and an
   `authz:check`-style gate) expects `tenantId` in both the WHERE and any cache key too. **Why:**
   defense in depth is a hard rule here (CLAUDE.md), not just an authz concern. **How to apply:**
   any new query against a tenant-schema table — add `eq(Table.tenantId, TenantId)` even if it
   looks redundant.

3. **When a spec names a specific mechanism ("the branch they switched to,
   `users.active_branch_id`"), don't substitute a nearby-but-different resolver because it's
   already imported and "close enough."** I built a recipient-timezone resolver on top of an
   existing function (`ResolveCallerScope`) that used the COARSER, non-active-branch-aware branch
   resolution (`ResolveEffectiveBranchId`) — reasoning it was "pre-existing, out of lane." The spec
   had a literal table row naming the mechanism it wanted (`FetchSessionIdentity`/
   `PickActiveBranch`). **Why:** "the existing helper resolves something similar" is not the same
   claim as "the existing helper resolves what was asked for" — check the spec's own named mechanism
   against what the reused function actually does, word for word, before treating a mismatch as
   acceptable scope discipline. **How to apply:** when a task names a specific function/column/table
   row explicitly, trace that exact path before reusing an adjacent one.

4. **Check file sizes (`wc -l`) on every file about to be edited BEFORE writing verbose doc
   comments, not after.** Two of my four target files were already within ~75 lines of this
   project's 600-line gate; my planned doc-comment style would have blown through it. Caught by the
   advisor, confirmed empirically, fixed by extracting a sibling file up front instead of writing
   first and discovering the gate failure after.

5. **A shared/common i18n catalog file's own header can forbid what you're about to do.**
   `catalogs/common.ts` explicitly says "do NOT edit this file for module-specific keys." I would
   have added an export-specific key there anyway out of momentum (it was the file I'd already
   opened for a REFERENCE key). **How to apply:** read a shared file's own header/doc comment for a
   scope rule before appending to it, even when it's the most convenient location.

General rule this reinforces: call `advisor()` after research, before the first line of code,
especially when the plan touches middleware ordering, tenant isolation, or a spec-named mechanism —
these are exactly the classes of error that pass every automated gate while still being wrong.

## Round 2 — caught at the "I believe I'm done" advisor call, before the report shipped

Two more, both real, neither caught by the 9 passing gates:

6. **A regex "shape check" on a value that must survive `Intl`/date-formatting is not validation —
   only `Intl` itself knows what `Intl` accepts.** `isPlausibleTimezone` was
   `/^[A-Za-z0-9_\-/]{1,64}$/` — it PASSES the literal string `"undefined"` (what `String(undefined)`
   produces) and `"/"`. A version-skewed or replayed API response missing a `timezone` field, piped
   through `setTimezone(data.timezone)` with no guard, would silently poison a year-long cookie with
   a non-value that crashes every localized page the next time `next-intl` tries to use it — a crash
   with no automated gate anywhere in reach of it (not a compile error, not a lint rule, not asserted
   by any test). **Fix pattern:** replace the regex with `try { new Intl.DateTimeFormat(undefined, {
   timeZone: value }); return true } catch { return false }`, AND add a symmetric guard at the
   writer (`if (!value?.trim()) return;`) so the boundary can't be poisoned even by a future caller
   that doesn't remember to check first. **How to apply:** any time a value flows from an API
   response into a long-lived client-side store (cookie, localStorage) and then into a
   throws-on-garbage API (`Intl`, `Date`, a strict parser), validate with that same API, not a
   hand-written pattern that only approximates its rules.

7. **A generated-file "real content" assertion (header text, cell values) is exactly the kind of test
   a header-formatting change breaks, and it will not show up in `tsc`/lint/a different test file.**
   Changing `Export.Generator.ts`'s `ResolveHeader` to decorate `type: "date"` column headers with a
   timezone suffix broke `Reports.Export.Streaming.test.ts` — an EXACT array-membership check
   (`expect(HeaderRow).toContain("Period Start")`) failed once the cell became `"Period Start
   (GMT)"`, in a file I hadn't looked at because the task named `Export.Job.Service.ts`, not the
   Reports module. Grepping for the changed behavior's OWN fingerprint
   (`type:\s*"date"`) across every integration/unit test file that generates and parses a real
   XLSX/CSV — not just the files the task explicitly named — found it before shipping. **How to
   apply:** after any change to shared formatting/generation code (headers, cell shaping, labels),
   grep test files for the literal old output your change alters, across the WHOLE test tree the
   change's chokepoint reaches, not just the module the task named. `[Est8Core: effective-timezone
   model]([[project_est8core_effective_timezone_2026-08-09]])` is the concrete case.

Both were caught by calling `advisor()` a second time right before declaring done, with all gates
already green — green gates are necessary, not sufficient; a second advisor pass at the "I'm
finished" checkpoint still earns its cost even after a clean gate run.
