# ADR-0003: Encryption Key Versioning, Secret Floors, and Purging Leaked Secrets from Git History

- **Status:** Accepted
- **Date:** 2026-09-04
- **Deciders:** Sabry
- **Project:** SmartestProp
- **Tags:** security, crypto, secrets, git
- **Related findings:** SEV-S-003 (+ امتداد كتالوج SMTP) · SEV-S-037 · SEV-S-038 (Plans/Audit-2026-09-03)

## Context

- الاعتماديات مشفّرة بـ AES-256-GCM بمفتاح واحد `ENCRYPTION_KEY` بلا إصدار؛ تدويره يكسر كل الصفوف المخزّنة، فلم يُدوَّر قط.
- `Scripts/Seed.ts` يحوي مفاتيح مزوّدين حقيقية وكلمة مرور أدمن افتراضية، وكتالوج `SystemSettings.Catalog.Features.ts` يحوي اعتماد SMTP حقيقياً يُبذَر مشفّراً في كل بيئة جديدة. كلها في تاريخ git حتى بعد حذفها من HEAD.
- `JWT_SECRET`/`APP_SECRET` يُقبلان بأي 16 حرفاً بلا فحص entropy.

القيود: المستودعان على GitHub (org `SmartestProp`)؛ Sabry وحده يدفع؛ عدد المستنسخين محدود ومعروف له.

## Decision

1. **تدوير فوري** (إجراء يدوي لـ Sabry، يسبق أي كود): كل مفتاح مزوّد ظهر في أي commit، كلمة مرور SMTP، كلمة مرور الأدمن الافتراضية، و`ENCRYPTION_KEY` و`JWT_SECRET` و`APP_SECRET` الحالية.
2. **إصدار المفاتيح:** صيغة ciphertext `v<n>:<iv>:<tag>:<ciphertext>`؛ `ENCRYPTION_KEYS="1:<hex>,2:<hex>"` و`ENCRYPTION_ACTIVE_KEY=2`؛ فكّ بأي إصدار مُدرَج، وتشفير بالنشط فقط؛ سكربت `crypto:rotate` يعيد تشفير الصفوف دفعات ويُبلغ بعدد `(مُعاد تشفيره / الكل)`؛ الصفوف القديمة بلا بادئة تُعامل كإصدار 1 حتى تكتمل الهجرة.
3. **أرضية الأسرار في الإنتاج:** ≥ 32 بايت وentropy ≥ 128 بت (رفض القيم القاموسية/المتكرّرة)؛ في التطوير تحذير فقط.
4. **لا أسرار في المصدر:** `Seed.ts` يقرأ `SEED_ADMIN_PASSWORD` و`SEED_<PROVIDER>_API_KEY` من البيئة (fail-fast في الإنتاج، توليد عشوائي يُطبع مرة في التطوير)؛ كتالوج SystemSettings لا يحمل `DefaultValue` غير فارغة لأي حقل `IsEncrypted: true`، مع بوابة CI تفشل عند المخالفة.
5. **إعادة كتابة التاريخ:** بعد التدوير، تُزال القيم من كامل تاريخ المستودع بـ `git filter-repo` (replace-text)، ويُبلَّغ كل من لديه clone بإعادة الاستنساخ. التنفيذ المحلي من الجلسة، والنشر من Sabry حصراً.

## Considered Options

### Option 1: إصدار + تدوير + إعادة كتابة التاريخ ← المختار
- **Pros:** يغلق التسريب الحالي وينهي «مفتاح لا يُدوَّر أبداً» ويحذف القيم من التاريخ.
- **Cons:** إعادة الكتابة تكسر كل clone وتحتاج تنسيقاً؛ migration لصيغة التخزين.

### Option 2: إصدار + تدوير بلا إعادة كتابة التاريخ
- **Pros:** لا كسر للمستنسخين.
- **Cons:** القيم المحروقة تبقى مرئية لكل من يقرأ التاريخ، وتبقى إشارة سيئة في أي مراجعة أمنية للعملاء.

### Option 3: تدوير فقط
- **Pros:** الأسرع.
- **Cons:** يترك المشكلة البنيوية؛ التدوير القادم سيُؤجَّل مجدداً للسبب نفسه.

### Option 4: KMS خارجي (AWS KMS / Vault)
- مرفوض الآن: خارج stack الشركة الحالي بلا سبب كافٍ، ويضيف تبعية تشغيلية على VPS واحد.

## Rationale

المحاور الحاكمة: **Security** (السرّ المكشوف في التاريخ مكشوف إلى الأبد) و**Maintainability** (التدوير يصبح روتيناً بسطر بيئة). Performance يُسقَط: فك التشفير في الذاكرة كما هو. Cost يُسقَط: لا مكوّن جديد. إعادة كتابة التاريخ قرار Sabry الصريح لأن أثره خارجي (المستنسخون).

## Consequences

### Positive
- ✅ تدوير المفاتيح بلا توقّف وبلا فقدان بيانات.
- ✅ لا سرّ في المصدر أو التاريخ؛ بوابة CI تمنع العودة.
- ✅ أرضية entropy تمنع `JWT_SECRET=dev-secret-123456` في الإنتاج.

### Negative (Trade-offs المقبولة)
- ⚠️ migration لصيغة التخزين + فترة انتقالية تُقرأ فيها الصفوف القديمة كإصدار 1.
- ⚠️ إعادة استنساخ إلزامية لكل من لديه نسخة؛ أي فرع محلي غير مدفوع يجب إعادة تطبيقه (rebase) على التاريخ الجديد.

### Risks
- 🚨 تدوير `ENCRYPTION_KEY` قبل نشر دعم الإصدارات = فقدان كل الاعتماديات — Mitigation: ترتيب صارم: (1) نشر دعم الإصدارات مع المفتاح القديم كـ v1، (2) إضافة v2 نشطاً، (3) `crypto:rotate`، (4) إزالة v1 بعد وصول العدّاد إلى الكل/الكل.
- 🚨 نسيان سرّ في التاريخ — Mitigation: تشغيل `gitleaks`/secret-scanning على كامل التاريخ قبل وبعد إعادة الكتابة وإرفاق العدّ.

## Migration Path

1. T-S-04 (إزالة الأسرار من المصدر + بوابة CI) — لا ينتظر شيئاً.
2. T-S-20 (الإصدار + الأرضية) — بعد قرار الترتيب أعلاه.
3. إعادة كتابة التاريخ — بعد التدوير الكامل وبتوقيت يحدّده Sabry.
