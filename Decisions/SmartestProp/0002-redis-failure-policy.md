# ADR-0002: Redis Failure Policy — Rate Limiter Fails Open with Alarm, Token Revocation Fails Closed

- **Status:** Accepted
- **Date:** 2026-09-04
- **Deciders:** Sabry
- **Project:** SmartestProp
- **Tags:** availability, security, redis, rate-limit, auth
- **Related findings:** SEV-S-025 · SEV-S-074 (Plans/Audit-2026-09-03)

## Context

`App.ts` يركّب `GlobalRateLimit` على كل `/api/*` ومخزنه Redis؛ أي تعطّل في Redis يُسقط الـ API كاملاً (SPOF). في المقابل `IsTokenRevoked` في `Auth.Middleware.ts` يعيد `false` عندما يغيب `RedisClient`، أي يقبل أي توكن مُبطَل بصمت. السلوكان متناقضان: الأول يفشل مغلقاً حيث لا يلزم، والثاني يفشل مفتوحاً حيث يلزم الإغلاق.

القيود:
- Redis موجود أصلاً في البنية (rate-limit · إبطال التوكنات · كاش الإعدادات) ولا بديل له قريب المدى.
- لا HA لـ Redis حالياً (نسخة واحدة على نفس الـ VPS).
- درس Est8Core: «حارس يفشل مفتوحاً بلا إنذار = لا حارس».

## Decision

1. **Redis تبعية أساسية:** health check عند الإقلاع يفشل سريعاً بلا Redis، و`/health` يعكس حالته، وإنذار (log error + metric) عند أي انقطاع.
2. **الـ rate limiter يفشل مفتوحاً مع إنذار:** عند خطأ Redis يمرّ الطلب، ويُسجَّل خطأ بمستوى `error` مرة كل 30 ثانية (لا لكل طلب)، ويُفعَّل **سقف محلي داخل العملية** للمسارات الغالية فقط (`AiUsage` · `PublicWidget`) حتى يعود Redis.
3. **فحص إبطال التوكن يفشل مغلقاً:** عند خطأ Redis يُرَدّ `503 SERVICE_UNAVAILABLE` (رسالة i18n)، **إلا** إذا وُجدت نتيجة «غير مُبطَل» لهذا `jti` في كاش داخل العملية عمرها ≤ 60 ثانية.
4. الاستثناء من (3): المسارات العامة غير المصادَقة (widget · health · docs) لا تمرّ بفحص الإبطال أصلاً فلا تتأثر.

## Considered Options

### Option 1: limiter مفتوح بإنذار · revocation مغلق ← المختار
- **Pros:** الإتاحة للقراءة والمحادثة تبقى أثناء التذبذب؛ لا يُقبل توكن مُبطَل بلا دليل؛ الكاش المحلي يمتصّ الانقطاعات القصيرة.
- **Cons:** أثناء الانقطاع تسقط حدود المعدّل العامة (يبقى السقف المحلي للغالي)؛ المستخدمون الذين انتهت صلاحية كاشهم يرون 503 حتى يعود Redis.

### Option 2: كل شيء يفشل مغلقاً (503)
- **Pros:** أبسط تفكيراً وأعلى أماناً.
- **Cons:** أي تذبذب = انقطاع كامل للمنصة والـ widget عند كل العملاء (تجربة SaaS غير مقبولة).

### Option 3: كل شيء يفشل مفتوحاً بإنذار
- **Pros:** إتاحة قصوى.
- **Cons:** يقبل توكنات مُبطَلة ويلغي كل الحدود أثناء الانقطاع؛ هو الوضع الحالي مع إنذار.

## Rationale

المحاور الحاكمة: **Availability** (المحادثة هي المنتج)، **Security** (الإبطال ضمانة لا تُلغى بصمت)، **Observability** (الإنذار جزء من القرار لا إضافة). Cost يُسقَط: لا مكوّن جديد. الخيار المختار يوزّع الفشل بحسب طبيعة كل ضابط: ضابط الإتاحة يميل للفتح، وضابط الهوية يميل للإغلاق.

## Consequences

### Positive
- ✅ لا يعود Redis نقطة فشل واحدة للقراءة والمحادثة.
- ✅ التوكن المُبطَل لا يُقبل أبداً بلا دليل حديث.
- ✅ الانقطاع يظهر فوراً في السجلات والمقاييس بدل الاكتشاف بالصدفة.

### Negative (Trade-offs المقبولة)
- ⚠️ نافذة 60 ثانية قد يبقى فيها توكن أُبطل للتوّ مقبولاً أثناء انقطاع Redis (مقبول: نفس نافذة TTL القصير للتوكن).
- ⚠️ السقف المحلي لكل عملية ليس دقيقاً عبر عدة عمليات (مقبول: نسخة PM2 واحدة اليوم — راجع ADR الإغلاق الآمن).

### Risks
- 🚨 إنذار غير موصول بقناة يقرأها أحد = لا إنذار — Mitigation: metric `redis_unavailable_total` + قاعدة تنبيه في Grafana/Sentry ضمن مهمة T-S-13.

## Migration Path

عند الحاجة لـ HA: Redis Sentinel أو Redis مُدار؛ لا يتغيّر شيء في هذا القرار لأن السياسة مستقلة عن الطوبولوجيا.
