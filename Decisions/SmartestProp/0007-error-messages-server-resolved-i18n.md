# ADR-0007: Error Messages — Server-Resolved i18n Catalog, Details Hidden in Production

- **Status:** Accepted
- **Date:** 2026-09-04
- **Deciders:** Sabry
- **Project:** SmartestProp
- **Tags:** i18n, api-contract, security, dx
- **Related findings:** SEV-S-028 · SEV-S-041 · SEV-S-075 · SEV-S-044 · SEV-S-087 · SEV-S-067 · SEV-C-043 (Plans/Audit-2026-09-03)

## Context

عقد الاستجابة موحّد (`{Success:false, Error:{Code, Message, Details}}`) لكن `Message` يسقط إلى الكود نفسه عند غياب المفتاح، فيصل `INSUFFICIENT_CREDITS` للمستخدم حرفياً؛ SSE يبثّ `err.message` الداخلية؛ `Details` تحمل كائنات الخطأ الخام (بما فيها `AppError` المتداخلة)؛ ردود البوت الحتمية ورسائل الاعتدال نصوص عربية مضمّنة؛ fr/tr ينقصهما 39% من المفاتيح؛ والعميل يعرض رسالة الخادم مباشرة في `ErrorRichBlock` و`KnowledgeDetailPanel`. درس Est8Core الحرفي: «`Message == Code` يصل للمستخدم — اقرأ `.code` وخريطة واحدة؛ ورسائل `refine` مُنتِج ثانٍ بلا بوابة».

القيود: أربع لغات؛ ثلاثة مستهلكين للأخطاء (لوحة التحكم، الـ widget المضمَّن، API خارجي/OAuth)؛ البريد والإشعارات تحتاج نصوصاً أيضاً.

## Decision

1. **الخادم مصدر الحقيقة:** كتالوج واحد `Errors.<Code>` في `Src/I18n/{Ar,En,Fr,Tr}`؛ كل `AppError` يحمل `Code` فقط، و`Message` يُحلّ في handler الأخطاء الموحّد بلغة الطلب (`Accept-Language` → لغة المستخدم/العميل → `en`). ينطبق على SSE (حدث `error` يحمل `{Code, Message}` محلولة) وعلى رسائل Zod/`refine` (تُعرَّف بمفاتيح لا نصوص) وعلى ردود البوت الحتمية ورسائل الاعتدال (تمرّر `Language` المحادثة).
2. **مفتاح غائب ⇒ رسالة عامة بلغة الطلب + log warn بالكود**؛ الكود لا يصل للمستخدم أبداً.
3. **`Details` في الإنتاج** = أخطاء التحقق المُهيكلة فقط (`[{Field, Code, Message}]`)؛ لا `stack` ولا كائنات خطأ خام؛ في التطوير تُضاف `Debug` منفصلة.
4. **العميل** يعرض `Error.Message` كما هي، ويحتفظ بخريطة next-intl صغيرة لأخطاء الشبكة/المهلة/عدم الاتصال فقط (لا استجابة من الخادم أصلاً).
5. **بوابة CI:** سكربت يجمع كل `Code` مُعرَّف في `Src/Common/Errors` وكل `I18nKeys.*` مُستخدَم، ويفشل عند أي كود بلا مفتاح في اللغات الأربع أو عند تفاوت مجموعات المفاتيح بين اللغات (يبدأ بإكمال fr/tr).

## Considered Options

### Option 1: الخادم يحلّ Message بلغة الطلب ← المختار
- **Pros:** كتالوج واحد يخدم لوحة التحكم والـ widget والـ API الخارجي والبريد؛ بوابة واحدة تمنع الانحراف.
- **Cons:** يجب إكمال 39% مفاتيح fr/tr قبل تفعيل البوابة؛ لغة الطلب يجب أن تُمرَّر في المسارات اللامتزامنة (درس Est8Core: «المسار اللامتزامن يسقط اللغة»).

### Option 2: العميل يترجم بالكود
- **Pros:** الخادم أبسط.
- **Cons:** كتالوجان يتباعدان؛ الـ widget المضمَّن والـ API الخارجي والبريد بلا رسائل؛ نفس الفشل المرصود في Est8Core.

## Rationale

المحاور الحاكمة: **Maintainability** (موطن واحد + بوابة) و**Security** (لا تسريب لرسائل داخلية عبر SSE/Details). Performance يُسقَط: حلّ مفتاح من خريطة في الذاكرة. Cost يُسقَط.

## Consequences

### Positive
- ✅ تأكيد عام في TestKit: لا استجابة يساوي فيها `Message` الـ `Code` (يفشل أي انحدار).
- ✅ الـ widget والـ API الخارجي يحصلان على رسائل مترجمة بلا كود في العميل.
- ✅ `Details` لم تعد قناة تسريب.

### Negative (Trade-offs المقبولة)
- ⚠️ عمل ترجمة أولي لإكمال fr/tr (يمكن توليد مسودة آلياً ومراجعتها).
- ⚠️ كل كود جديد يحتاج أربعة مفاتيح قبل أن يمرّ CI (مقصود).

### Risks
- 🚨 مسار لامتزامن (أحداث، مهام مجدولة، بريد) بلا لغة ⇒ يسقط إلى `en` بصمت — Mitigation: `Language` حقل إلزامي في حمولة كل حدث يُنتج نصاً للمستخدم، وبوابة نوع تفرضه.

## Migration Path

T-S-15 (الخادم) ثم T-C-04 (العميل يزيل أي عرض للكود). بوابة CI تُفعَّل بوضع تحذير حتى اكتمال fr/tr ثم تُحوَّل إلى فشل.
