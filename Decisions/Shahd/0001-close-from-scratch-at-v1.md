# ADR 0001 — إغلاق خط from-scratch عند v1 وإبقاء قيد الملكية كما هو

- **التاريخ:** 2026-07-18
- **الحالة:** مقبول (قرار Sabry بعد تقييم CTO صريح)
- **المشروع:** Shahd (شهد) — code LM من الصفر

## السياق

بعد اكتمال MicroChat ‏(6.56M، ‏20k خطوة SFT) ونجاح فحص القبول الثلاثي (تحية → tool call → هوية في محادثة واحدة multi-turn)، طُرح سؤال المسار: هل نستمر from-scratch بقيد "لا أوزان مفتوحة"، أم نعدل؟

**الحقائق الحاكمة:**
- سقف الجهاز الحالي (CPU) هو Micro/Mini ‏(6-36M). المساعدات المفيدة فعلاً تبدأ من ~1B+ باراميتر — فجوة حوسبة ×1000 لا تُغلق بأي تحسين.
- ‏tier ‏Small ‏(126M) يحتاج سنوات على CPU؛ أي تقدم حقيقي بعد Mini يستلزم GPU مؤجراً.
- مطاردة robustness لصياغات خارج التوزيع في موديل صغير = whack-a-mole ضد جدار سعة (عوائد متناقصة).
- القيمة الحقيقية المبنية = **المنصة** (محرك بيانات، وصفات SFT، بروتوكول أدوات، agent loop + trace، داشبورد، serving، resume) + المعرفة العميقة — لا الموديل نفسه.

## القرار

1. **إغلاق خط from-scratch عند v1** وإعلانه: ‏GH Release ‏v0.1.0 بالـ checkpoints الأربعة + ‏RELEASE-NOTES + سكرين شوتس.
2. **قيد الملكية يبقى كما هو** — لا أوزان مفتوحة. لا يُعاد فتح القرار إلا يوم يُراد منتج فعلي لعملاء، وساعتها يكون قراراً تجارياً واعياً (منصة مملوكة + عقل مفتوح الرخصة مدرَّب ببياناتنا) لا تنازلاً هندسياً.
3. لا مطاردة إضافية لتحسينات سلوكية على الموديلات الصغيرة بعد v1 (باستثناء ما يخدم المنصة نفسها، مثل KV-cache للـ serving).

## البدائل المرفوضة

- **مواصلة التعميق from-scratch بلا حد**: عائد تعلمي متناقص وتكلفة فرصة عالية على وقت Sabry.
- **التحول الهجين الآن**: لا حاجة منتج حالية تبرره؛ يظل خياراً موثقاً للمستقبل.

## النتائج المترتبة

- ‏v1 = برهان قدرة + IP + أساس تعليمي/استشاري؛ المنصة جاهزة لأي عقل مستقبلي.
- أي عمل قادم على شهد يُقاس بسؤال: هل يخدم المنصة أم يطارد سقف موديل صغير؟
