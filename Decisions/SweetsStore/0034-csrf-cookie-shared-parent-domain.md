# ADR-0034 — مشاركة كوكي CSRF بين نطاقي الواجهة والـ API

- **الحالة:** مقبول
- **التاريخ:** 2026-10-12
- **Deciders:** Sabry
- **يمسّ:** مصادقة المتصفح بين `Client/` و`Server/`
- **السياق والتنفيذ:** [خطة إصلاح CSRF](../Plan/Auth-Csrf-Cross-Subdomain.md)
- **يمدّد:** [ADR-0004](0004-auth-jwt-refresh-rotation-denylist.md)

## السياق

تُخدَم الواجهة من `dawwar.futuresolutionsdev.com` والـ API من
`dawwar-server.futuresolutionsdev.com`. كوكي CSRF ذات `Domain` غير محدد تبقى host-only على نطاق
الـ API: يرسلها المتصفح إلى الـ API، لكن صفحة المتجر لا تستطيع قراءتها لإضافة القيمة نفسها إلى
`x-csrf-token`. ينتج عن ذلك رفض refresh وطلبات الكتابة المحمية برسالة CSRF غير صالح.

## القرار

1. يدعم Server إعدادًا اختياريًا `AUTH_COOKIE_DOMAIN`. في الإنتاج الحالي يضبط إلى
   `.futuresolutionsdev.com`، كي يقرأه كل من أصل الواجهة والـ API.
2. يطبّق النطاق المشترك على كوكي `dm_csrf` فقط.
3. تبقى كوكي `dm_rt` host-only على نطاق API، و`httpOnly` و`Secure` في الإنتاج، وبمسار
   `/api/v1/auth`.
4. تبقى حماية `SameSite=Strict` والتحقق من `Origin` ومقارنة الكوكي بالهيدر مطبّقة.
5. يظل الإعداد غير مضبوط محليًا؛ لا يتغير سلوك التطوير.

## البدائل

- **نقطة تهيئة CSRF مع إبقاء الكوكي host-only:** أكثر تعقيدًا وتتطلب طلبًا إضافيًا قبل refresh؛
  رُفضت لصالح إعداد كوكي مشترك بعد موافقة المالك.
- **توسيع refresh cookie إلى النطاق الأب:** رُفض؛ لا حاجة لتعريض كوكي الجلسة لكل النطاقات الفرعية.

## الأثر الأمني

يصبح CSRF token مقروءًا لكل origin تحت `.futuresolutionsdev.com`؛ لذلك يفترض هذا القرار أن كل
النطاقات الفرعية موثوقة وتحت الإدارة. لا ينتقل refresh token إلى النطاق الأب، وتظل قيود Origin
وSameSite قائمة. إذا لم تعد النطاقات الفرعية موثوقة، يجب استبدال هذا القرار بتدفق تهيئة CSRF
مقيّد بالأصل أو وسيط same-origin.
