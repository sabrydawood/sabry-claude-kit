# Anti-pattern: قيمة Joi المُحوَّلة تُحسَب ثم تُرمى

## What

ميدلوير تحقّق يستدعي `schema.validate(req.body)`، يستخدم `error` فقط، **ويهمل `value`** —
فيصل الـ handler المدخل الخام لا المُحوَّل. النتيجة: `.default()` و`.trim()` و`.lowercase()`
وتحويل الأنواع و`.custom()` كلها **بلا أثر**، بينما تبدو في الـ schema كأنها تعمل.

```js
// ❌ الشكل المعطوب
let ReqKey = { ...req[key] };                       // نسخة — التعديل عليها غير مرئي أصلاً
// eslint-disable-next-line no-unused-vars
let { error, value } = Schema[key].validate(ReqKey); // value لا يُكتب في أي مكان
if (error) return Reject(error);
return next();                                       // req.body لم يتغيّر
```

## Why it's wrong

الخطورة ليست في السلوك اليوم، بل في أنه **يقرأ صحيحاً**. من يكتب schema جديدة يفترض
منطقياً أن `Joi.number()` تعني «سأستلم رقماً»، وأن `.default(10)` تعني «لو غاب سأستلم 10».
كلاهما خطأ في هذا الشكل، **بلا أي إشارة**:

| ما كتبتَه | ما تتوقّعه | ما تستلمه فعلاً |
|---|---|---|
| `Joi.number()` | `5` | `"5"` — نص |
| `.default(10)` | `10` | `undefined` — المفتاح غائب |
| `.trim()` | `"ali"` | `"  ali  "` |
| `.lowercase()` | `"ali@x.com"` | `"Ali@X.com"` |
| `.custom(v => v.trim())` | القيمة المُنظَّفة | القيمة الخام — الـ `return` مُهمَل، والـ `throw` وحده يعمل |

خطر خاص: `.custom()` تبدو أداة تعقيم، وهي هنا أداة **رفض** فقط. من يستخدمها للتنظيف
يظن أنه عقّم مدخلاً، وقد مرّره خاماً.

## When seen (سياق)

- المشروع/الـ stack: **Master-V** — Express + Joi، `Backend/Server/Validation/Http/Validator.js:23`
- التاريخ: **2026-08** — كشفها `security-reviewer` أثناء مراجعة تغيير غير ذي صلة (عقد العملة)
- الـ `// eslint-disable-next-line no-unused-vars` فوق السطر مباشرةً ⇒ الـ linter **رصدها،
  وأُسكِت** بدل أن تُصلَح. هذا وحده مؤشّر يستحق الانتباه في أي مراجعة.
- التكلفة الفعلية: **صفر حتى الآن** — مسح على 13 ملف schema أثبت أن لا شيء يعتمد على
  تحويل مُهمَل. أُصلح بالتوثيق لا بالكود، للسبب في الأسفل.

## Correct Approach

**في كود جديد** — اكتب القيمة المُتحقَّق منها:

```js
const { error, value } = Schema[key].validate(req[key]);
if (error) return Reject(error);
req[key] = value;              // ← السطر الغائب
return next();
```

**في نظام قائم** — 🔴 **لا تضف هذا السطر دفعة واحدة.** كل `.default()` و`.custom()`
وتحويل نوع في المشروع سيُفعَّل **في اللحظة نفسها**، وأغلبها لم يعمل قط فلا اختبار يحرس
الفرق. الترتيب الآمن:

1. امسح كل الـ schemas: `.default(` · `.trim()` · `.lowercase()` · `.custom(` · تحويلات النوع
2. لكل موضع: هل المستودع يدافع عن نفسه أصلاً؟ (`const { X = [] } = Filter` · `SafeInt` · `SafeRate`)
3. لا يعتمد أحد على التحويل ⇒ **وثّق ولا تُصلح** — الإصلاح مخاطرة بلا مقابل
4. يعتمد أحد ⇒ أصلح **هذا الموضع** في المستودع، لا الميدلوير
5. الميدلوير يُصلَح أخيراً، بعد أن يصير السطر بلا أثر مقاس

**وفي الحالتين:** المستودع لا يثق في طبقة التحقّق. `SafeInt`/`SafeDecimal`/`SafeRate` تُعيد
الاشتقاق من الخام — وهي ما جعل الخلل غير ضار هنا، **بالمصادفة لا بالتصميم**.

## Detection

- **Linter:** أي `eslint-disable` لـ `no-unused-vars` فوق destructuring فيه `value` أو
  `data` أو `result` من دالة تحقّق ⇒ افحصه يدوياً. الـ disable هو الدليل.
- **مراجعة:** في أي ميدلوير تحقّق، اسأل سؤالاً واحداً: **«أين تُكتب النتيجة؟»**
  لا جواب ⇒ الميدلوير بوّابة لا محوّل، ووثّق ذلك في رأسه.
- **اختبار:** أرسل `{ Field: "  5  " }` على schema فيها `Joi.number()` واقرأ ما يصل
  المستودع. لو وصل `"  5  "` فالتحويل مُهمَل.
- **علامة إنذار في الـ schema:** `.custom()` تُعيد قيمة **مختلفة** عن مدخلها. في هذا الشكل
  الفرق يُرمى بصمت.
